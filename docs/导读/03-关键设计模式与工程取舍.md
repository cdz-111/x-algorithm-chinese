# 03 — 关键设计模式与工程取舍

前两篇讲"是什么"，这篇讲"为什么这么设计"。这套代码里有 6 个模式，任何做推荐/排序/风控流水线的人都值得直接借鉴。

## 1. Prod / Mock 双实现的依赖注入

**现象**：`home-mixer/clients/` 下几乎每个客户端文件（19 个）里都成对定义了 `ProdXxxClient` 与 `MockXxxClient`，例如 `GizmoduckClient / MockGizmoduckClient / ProdGizmoduckClient`（`home-mixer/server.rs:6`）。流水线本身也提供两套构造函数：

```rust
ForYouCandidatePipeline::new(scored_posts_server, shard, datacenter)  // 生产：真实客户端
ForYouCandidatePipeline::mock(scored_posts_server)                     // 本地：全部 Mock
```

两条路径最终都进同一个 `build(...)`，**装配逻辑只有一份**（`for_you_candidate_pipeline.rs:169`）。

**为什么好**：
- 本地可跑整套流水线（不依赖任何内部服务），开发和调试门槛极低；
- 单测里换掉任意一个依赖即可构造边界场景（"如果社交图服务返回空会怎样"）；
- 生产装配是集中式的，一眼能看到这条链路依赖了哪些外部服务 —— 这也是**服务依赖图**的天然来源。

## 2. Feature Switch + 参数化：所有"魔法数字"都是可调开关

**现象**：`home-mixer/params/param.rs` 用宏注册参数，例如：

```rust
param!(FavoriteWeight, f64, "rust_home_mixer_favorite_weight", 0.5);
param!(ReplyWeight,    f64, "rust_home_mixer_reply_weight",    5.0);
param!(ReportWeight,   f64, "rust_home_mixer_report_weight", -234.0);
```

代码里**不出现硬编码权重**，一律 `params.get(ReplyWeight)`（`scorers/ranking_scorer.rs:64`）。

**分层灰度**：`QueryBuilder::build()` 里用 `decider.with_recipient(viewer_id)` 生成按用户分流的实验分配器（`server.rs:122`），配合 `FeatureSwitches` 支持按用户/角色批量下发不同参数。

**为什么好**：
- 调参不需要发版，紧急情况（恶意内容突增）可以实时收紧；
- 实验与线上走同一套代码路径，避免"实验环境跑得好、上线就不对"；
- 参数名自带命名空间（`rust_home_mixer_*`），多服务共存不冲突。

> 值得注意的细节：`param.rs` 里留有团队对权重语义的讨论注释，例如澄清"一次举报并不等于抵消 468 个赞"，因为模型预测的是**发生概率**而不是**计数**（`params/param.rs:294`）。这类决策留痕对后续接手者极有价值。

## 3. 分级处理：把算力花在刀刃上

整条链路是**三段式**的：

```
粗筛（规则、便宜）   →   打分（模型、中等）   →   合规校验（最贵）
18 个 filter          3 个 scorer              7 hydrator + 3 filter
作用于全部召回         作用于存活候选            只作用于 Top-K
```

典型证据：可见性过滤（VF）这种需要额外服务调用的重校验，放在 **post_selection** 阶段（`phoenix_candidate_pipeline.rs:417`），只对最终入选的几十条执行。反过来，`AgeFilter`、`DropDuplicatesFilter` 这种纯内存判断放在最前面，用最便宜的代价砍掉大部分候选。

**可带走的规则**：任何流水线都应回答"这个阶段的单位成本是多少、作用在多少条候选上"，然后按成本从低到高排序。

## 4. 副作用与主链路彻底解耦

```rust
let side_effects: Arc<Vec<Box<dyn SideEffect<Q, C>>>> = Arc::new(vec![ ... ]);
fn side_effects(&self) -> Arc<Vec<Box<dyn SideEffect<Q, C>>>> { Arc::clone(&self.side_effects) }
```

框架执行时用 `futures::future::join_all` 并行跑完所有副作用（`candidate_pipeline.rs:12`），且它们**不参与响应构建**。

**为什么好**：埋点、日志、缓存回写这些"必须做但不该影响延迟"的动作被隔离；任何一个副作用变慢或失败，都不会拖垮用户请求。用 `Arc` 共享而非每次 clone，也避免了每请求重新构造副作用列表。

## 5. 可观测性是一等公民

这套代码在可观测性上的投入值得单独看：

| 机制 | 实现位置 | 作用 |
|---|---|---|
| 阶段级埋点 | `PipelineStage` 枚举 + `StageStats`（`candidate_pipeline.rs:24`） | 按 `(requests, stage, component)` 打标签，能定位"哪个阶段吃掉了延迟/砍掉了候选" |
| 分布式追踪 | B3 header 解析 + `root_span`（`server.rs:40`、`server.rs:150`） | 跨服务 trace 贯通 |
| 强制采样 | `params::TRACE_USER_IDS` 命中即 `force_sample()`（`server.rs:86`） | 线上疑难问题可按用户精准抓全链路 |
| 结果集统计 | `FINAL_RESULT_SIZE_SCOPE` / `FINAL_RESULT_EMPTY_SCOPE`（`candidate_pipeline.rs:20`） | 监控"空结果率"这类业务级指标 |

**尤其重要的是 `PipelineResult` 保留三份候选集合**（retrieved / filtered / selected，`candidate_pipeline.rs:56`）：有人问"为什么我的帖子没被推荐"，可以直接从 `filtered_candidates` 里查出是被哪个过滤器拦下的 —— 这是把"可解释性"做进架构，而不是事后补日志。

## 6. 模型调用的重试与降级由开关驱动

Phoenix 打分不是裸调：

```rust
PredictionDispatch {
    prod: phoenix_client,
    paths: prediction_paths,          // 支持 xDS 动态路由
    max_retries_key: "rust_home_mixer_phoenix_xds_max_retries",
    enable_fallback_key: "rust_home_mixer_phoenix_enable_fallback",
}
```

（`phoenix_candidate_pipeline.rs:394`）

**要点**：连"重试几次""是否允许降级"都是 Feature Switch。这意味着故障时可以**不改代码、不发版**地调整策略（例如模型服务抖动时临时关掉重试、直接走降级路径）。对推荐系统这种"延迟敏感 + 依赖重"的场景，这是必要的生存能力。

## 7. 语言与架构取舍

| 决策 | 理由（从代码结构可验证） |
|---|---|
| **Rust 写编排层** | home-mixer / candidate-pipeline / thunder 全是 Rust：无 GC 停顿、并发安全、单机延迟可控 |
| **gRPC + Protobuf** | 服务入口与跨服务数据（`xai_home_mixer_proto`）统一 IDL，跨语言（Scala/Python 模块）互通 |
| **单仓多模块** | 召回（thunder）、模型（phoenix）、治理（botmaker）、聚类（simclusters）同仓：接口变更能一次性改完 |
| **框架与业务分离** | `candidate-pipeline` 不含任何业务逻辑，业务全在 `home-mixer/candidate_pipeline/` 的装配里 |
| **不可变 Query** | `Arc<Q>` 贯穿全链路（`PipelineResult.query`） |

## 8. 一份可复用的检查清单

如果你在设计自己的推荐/排序流水线，可以直接用这份清单对照：

- [ ] 每个阶段是否有统一的 trait 抽象，新增组件是否需要改框架？
- [ ] 外部依赖是否有 Mock 实现，能否脱离内网跑通全链路？
- [ ] 所有阈值/权重是否参数化，能否不发版调整？
- [ ] 过滤阶段是否保留了"为什么被丢"的完整记录？
- [ ] 昂贵校验是否只作用于入选集？
- [ ] 埋点/日志/缓存回写是否与主链路解耦？
- [ ] 是否有 holdout 机制来度量推荐的真实增量？
- [ ] 模型调用是否有开关驱动的重试与降级？

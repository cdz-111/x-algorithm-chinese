# 01 — 请求生命周期与流水线框架

本篇回答两个问题：**一次 `For You` 请求发生了什么**，以及**`candidate-pipeline` 框架怎么把推荐流程抽象成可复用组件**。

> 所有结论均来自仓库代码，括号内为源文件路径，可自行核对。

## 1. 全局视角：两条内容来源 + 一个编排层

X 的 `For You` 信息流由**两股内容**混合而成，这是理解整个仓库的第一前提：

| 内容来源 | 含义 | 由谁提供 |
|---|---|---|
| **In-network（网络内）** | 你关注的人发的帖子 | `thunder` 模块（Rust，内存存储 + Kafka 增量） |
| **Out-of-network（网络外）** | 你没关注、但算法认为你会喜欢的帖子 | `phoenix` 模块（模型召回 + 排序） |

`home-mixer` 是**编排层**：它不生产候选、不训练模型，负责把 Query 补全、把各路候选取回来、过滤、打分、混排、写副作用日志，最后吐出 Feed 列表。

```
┌──────────────┐   ┌──────────────┐
│   Thunder    │   │   Phoenix    │   ← 两条召回来源
│ (in-network) │   │(out-of-net)  │
└──────┬───────┘   └──────┬───────┘
       └────────┬─────────┘
                ▼
        ┌───────────────┐
        │  home-mixer   │  ← 编排：补齐 → 过滤 → 打分 → 选择 → 混排 → 副作用
        │  (Rust/gRPC)  │
        └───────┬───────┘
                ▼
        For You / Following / Ranked Following …Feed
```

## 2. 服务入口与 Query 构建

启动入口在 `home-mixer/main.rs`，用 `tonic` 起 gRPC 服务（154 行，很短，适合先读）。

真正的请求处理在 `home-mixer/server.rs`（997 行），核心是 `QueryBuilder::build()`：

1. **参数校验**：`viewer_id == 0` 直接返回 `invalid_argument`（`server.rs:83`）。
2. **强制采样**：命中 `params::TRACE_USER_IDS` 的用户强制开 trace，便于线上排障（`server.rs:86`）。
3. **并行拉取用户数据**：`tokio::join!` 同时取 `viewer_data`（用户画像/角色/静音词等）与 `resurrection_time`（账号复活时间），**避免串行 RTT**（`server.rs:90`）。
4. **Feature Switch 求值**：`evaluate_feature_switches(...)` 把所有开关解析成一个 `Params` 对象，贯穿整条流水线 —— 这是 X 全量灰度/实验的基础设施。
5. **组装 `ScoredPostsQuery`**：把 proto 请求 + 用户数据 + 参数 + decider + 设备信息（UA、时区、网络类型、客户端版本）+ 影子流量标记等，合成一个贯穿全链路的 Query 对象（`server.rs:112-146`）。**注意它带上了 `seen_ids` / `served_ids`**，即"已经看过/已下发过"的帖子，供后续过滤去重。
6. **建 trace span**：`root_span` 标注 endpoint、trace id、user、b3 采样位（`server.rs:150`）。

> **设计要点**：Query 是**不可变地往下传**的（`Arc<Q>`），每个阶段只读它，不会出现"某个组件偷偷改了用户偏好"的隐蔽 bug。

## 3. 流水线框架：candidate-pipeline 的 10 个阶段

`candidate-pipeline/` 只有 11 个文件，是整个仓库的**架构钥匙**。它定义的阶段枚举（`candidate-pipeline/candidate_pipeline.rs:24`）：

| 阶段 | 抽象 trait | 作用 |
|---|---|---|
| `QueryHydrator` | `QueryHydrator<Q>` | 补全**查询**（例如：拉取历史已看、上次请求时间） |
| `DependentQueryHydrator` | 同上 | 依赖其他补水结果才能算的查询补水（第二批） |
| `Source` | `Source<Q, C>` | **召回候选**（多源并行） |
| `Hydrator` | `Hydrator<Q, C>` | 给**候选**补字段（作者信息、媒体信息、互动数…） |
| `Filter` | `Filter<Q, C>` | 过滤候选（去重、过期、拉黑、已看…） |
| `Scorer` | `Scorer<Q, C>` | 打分（模型分、加权聚合、多样性） |
| `Selector` | `Selector<Q, C>` | **选择/排序**，输出 Top-K 或混排结果 |
| `PostSelectionHydrator` | `Hydrator<Q, C>` | 选中后再补字段（只给最终少量候选做，省算力） |
| `PostSelectionFilter` | `Filter<Q, C>` | 选中后再做合规/质量兜底校验 |
| `SideEffect` | `SideEffect<Q, C>` | 副作用（写 Kafka、写缓存、埋点），**不阻塞主链路** |

统一执行顺序在 `execute_stages()`（`candidate_pipeline.rs:111`）：

```
hydrate_query → hydrate_dependent_query → fetch_candidates(sources)
  → hydrate → filter → score → select
  → hydrate_post_selection → filter_post_selection
  → 截断到 result_size → 跑 side_effects
```

三份产出集合保留在 `PipelineResult` 里（`candidate_pipeline.rs:56`）：

- `retrieved_candidates`：召回后
- `filtered_candidates`：**所有被过滤掉的**（含选中后被过滤的）——这是线上排障的黄金数据，能回答"我的帖子为什么没被推荐"
- `selected_candidates`：最终选中的

**两个易被忽略的工程细节**：

1. `side_effects` 用 `Arc<Vec<...>>` 共享持有，执行时**并行 `join_all`**，不阻塞返回（`candidate_pipeline.rs:12`）。
2. 每个阶段都有 `StageStats` / span 埋点（`pipeline_summary`），按 `(requests, stage, component)` 打标签，所以能按阶段拆解耗时与通过率。

## 4. 六条流水线并行存在

`home-mixer/candidate_pipeline/` 下定义了多条业务流水线，共用同一套框架：

| 文件 | 用途 |
|---|---|
| `for_you_candidate_pipeline.rs`（326 行） | For You 主 Feed 的**混排层** |
| `phoenix_candidate_pipeline.rs`（1094 行） | **真正的推荐主链路**（召回→过滤→打分→TopK） |
| `following_candidate_pipeline.rs`（294 行） | 关注流 |
| `ranked_following_candidate_pipeline.rs`（227 行） | 排序版关注流 |
| `reverse_chron_posts_pipeline.rs`（238 行） | 纯倒序（时间线） |
| `phoenix_scores_pipeline.rs`（450 行） | 只产 Phoenix 分数（供其他服务消费/调试） |

## 5. For You 一条请求的完整链路

以 For You 为例（`home-mixer/for_you_server.rs` → `for_you_candidate_pipeline.rs`）：

```
gRPC 请求
  ↓ QueryBuilder::build()                     ← 组装 ScoredPostsQuery（server.rs）
ForYouFeedServer::get_for_you_feed_urt()      ← 入口，做 URT 序列化（for_you_server.rs:44）
  ↓ get_for_you_feed()                        ← 校验 TEST_USER_IDS 后执行流水线
ForYouCandidatePipeline::execute(query)       ← 框架统一执行
  ├─ query_hydrators: ServedHistory / PastRequestTimestamps
  ├─ sources（7 路并行）:
  │    ScoredPostsSource  ←── 内部调用 ScoredPostsServer → PhoenixCandidatePipeline（主链路！）
  │    AdsSource / WhoToFollowSource / PromptsSource
  │    PushToHomeSource / JetfuelFrameSource / FeedSurveySource
  ├─ filters: PushToHomeDedupFilter
  ├─ selector: BlenderSelector                ← 把上面各源的结果**混排**
  ├─ post_selection_filters: AdAdjacentServedFilter（广告相邻位控制）
  └─ side_effects: 广告曝光日志 / 已下发历史 / seen_ids 上报 Kafka / 客户端事件 / 响应统计 …
  ↓ result.selected_candidates
feed_log 记录 → URT 二进制时间线序列化 → 返回
```

关键点：**`ForYouCandidatePipeline` 本身不做推荐打分**，它的 `scorers()` 返回空数组——真正的召回与打分发生在它调用的 `ScoredPostsSource` 里面（即 `PhoenixCandidatePipeline`）。这一层只负责"把帖子、广告、关注推荐、提示卡、调查卡等**多种内容类型混排**成一条 Feed"。
